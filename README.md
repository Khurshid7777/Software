# Ishonch — MVP маркетплейса б/у товаров (Ташкент)

Telegram Mini App + бот + API. Стратегия запуска **B + D → A**: сначала «Tekshir» (проверка чужих объявлений), затем кабинет продавца, затем каталог.

## Быстрый старт (локально)

```bash
pnpm install
cp .env.example .env            # заполнить BOT_TOKEN, ANTHROPIC_API_KEY, ADMIN_TELEGRAM_IDS
docker compose up -d postgres minio minio-init
pnpm db:migrate && pnpm db:seed # таблицы, категории, 20 моделей в справочнике цен, настройки
pnpm --filter @ishonch/api dev:seed-catalog   # (по желанию) 7 демо-объявлений для каталога и помощника
pnpm dev:api                    # http://localhost:3000
pnpm dev:bot
pnpm dev:miniapp                # http://localhost:5173 (проксирует /api → :3000)
```

Mini App в Telegram должен открываться по HTTPS: для разработки пробросьте `:5173` через туннель (cloudflared/ngrok) и укажите адрес в `MINIAPP_URL` и в @BotFather (Bot Settings → Menu Button / Mini App).

**Без ключа Claude**: `pnpm --filter @ishonch/api dev:mock` поднимает API с детерминированным AI из фикстур, фейковым STT и «публикацией в канал» в лог, и печатает подписанный `INIT_DATA`. Откройте `http://localhost:5173/?initData=<INIT_DATA>` — приложение работает вне Telegram (`&screen=sell`, `&startapp=listing_<id>` — сразу нужный экран).

## Продакшн (VPS в Узбекистане)

```bash
cp .env.example .env   # реальные значения
docker compose up -d --build
```

Сервисы:

- `postgres` (16);
- `minio` (+ bucket) — образ задаётся `MINIO_IMAGE`, закрепите проверенный тег;
- `api` — при старте применяет миграции под блокировкой, поэтому реплики можно поднимать одновременно; затем сид, воркер фоновых задач и ежечасные задачи (их выполняет одна реплика);
- `bot` — webhook при заданном `BOT_WEBHOOK_URL` (nginx проксирует `/tg-webhook` → `bot:8081`), иначе long polling через runner;
- `miniapp` — nginx, отдаёт статику и проксирует `/api` → `api`.

Перед `miniapp` нужен TLS-прокси. Логи API — в `docker logs` и `./logs/api.log`; ротация — `deploy/logrotate-ishonch` (инструкция внутри файла).

Интеграционные тесты API (`apps/api/test/*.app.test.ts`, файлы запускаются по очереди) используют PostgreSQL из `TEST_DATABASE_URL` (по умолчанию локальный) и пропускаются, если БД недоступна. CI (`.github/workflows/ci.yml`) на каждый push и PR: typecheck, проверка словарей, миграции и сид на PostgreSQL 16, тесты, сборка Mini App; отдельной задачей — e2e на Playwright (отчёт прикладывается при падении).

Диагностика: каждый ответ API несёт заголовок `x-request-id` (берётся из входящего, если его поставил прокси), он же пишется в логи и возвращается в теле ошибки 500. `GET /health` проверяет БД и отдаёт версию (`APP_VERSION`) и аптайм, при недоступной БД — 503; `GET /health/live` — простая проверка живости процесса.

## Как устроено

**Авторизация.** Mini App шлёт `Authorization: tma <initData>`; API проверяет HMAC-подпись по токену бота и срок `auth_date`, создаёт пользователя. Бот ходит в API с `Authorization: Internal <INTERNAL_API_TOKEN>` + `X-Telegram-User`. БД есть только у API. Админы задаются через `ADMIN_TELEGRAM_IDS`.

**AI.** Все вызовы идут через `apps/api/src/ai/aiService.ts`: он загружает версионированный промпт из `packages/shared/prompts/<id>.v<N>.md` (front matter: модель, max_tokens, effort), проверяет месячный лимит (`ai_monthly_limit_usd`, по умолчанию $50, предупреждение в логе с 80%), валидирует структурированный ответ (zod) и пишет токены и стоимость в `ai_usage`. Модели: `claude-haiku-5-5` для всего (включая модерацию этапа 4), `claude-opus-5-5` только для помощника покупателя (этап 3). Обе меняются через env.

**Модуль B — пайплайн** (`apps/api/src/modules/checks/pipeline.ts`):
1. `check_extract` — структура объявления из скриншотов/текста (обезличенно: имена, телефоны, ссылки не извлекаются; дополнительно вычищаются регулярками).
2. Рыночная цена: справочник `price_reference` (нечёткий поиск pg_trgm, но номер модели и объём памяти должны совпасть) → медиана каталога (появится в модуле A) → оценка AI с пометкой «приблизительно».
3. Скоринг риска по правилам раздела 7 (`packages/shared/src/risk/defaultRules.json`, переопределяется ключом `risk_rules` в таблице `settings` без релиза).
4. `check_report` — плюсы/минусы, 5 вопросов продавцу, доп. красные флаги и корректировка риска (±15; понизить уровень, определённый правилами, AI не может).
5. Чек-лист осмотра — статичный по категории из i18n (дешевле и надёжнее AI).

Ограничения: 5 проверок в день (`checks_per_day` в `settings`), только ссылка → просьба прислать скриншот/текст (сайты не парсим), скриншоты не сохраняются, в `checks` лежат только обезличенные поля.

**Модуль D — кабинет продавца** (`apps/api/src/modules/listings/`):
1. `POST /listings/drafts` — 1–10 фото и/или голосовое и/или текст. Фото: поворот по EXIF, ≤1600px JPEG в хранилище, копия ≤1024px для AI, perceptual hash (dHash) для поиска дублей на этапе 4. Голос → `SpeechToText` (Whisper-совместимый HTTP API, провайдер меняется в `.env`).
2. `listing_analyze` — категория, модель, характеристики **только видимые или названные продавцом**, видимые дефекты, 1–3 уточняющих вопроса (RU+UZ с вариантами ответа), советы по фото. Цена: быстрая (−10%, не ниже минимума рынка) / рыночная / максимальная из справочника, иначе приблизительная оценка AI.
3. `POST /listings/:id/generate` — `listing_generate` пишет заголовок и описание на RU и UZ (латиница) только по подтверждённым фактам и ответам; телефоны/ссылки вычищаются. Ответ про память уточняет модель → цена пересчитывается.
4. Редактирование (`PATCH`), фото (добавить/удалить), район, состояние, режимы доставки (`delivery_only`, `cod_seller`; `cod_platform` — только при `COD_PLATFORM_ENABLED=true`), кто платит за доставку.
5. `POST /listings/:id/publish` — нужен телефон (Mini App вызывает `requestPhoneAccess`, Telegram отправляет контакт боту, бот сохраняет его через `/internal/phone`; покупатели номер не видят), ≥1 фото, тексты и цена; частник — до 10 активных, магазин — без лимита. Статус `active` на 30 дней (AI-модерация со статусом `pending` — этап 4). Пост в выбранные каналы продавца уходит сразу (фото + цена + описание, кнопка «Купить с доставкой» → Mini App `startapp=listing_<id>`).
6. Управление: «Мои объявления» (активные / черновики / проданные / архив), «Продано» через Ishonch или в другом месте, поднятие раз в 3 дня, архив и возврат в продажу, статистика (просмотры; избранное и заявки начнут считаться на этапах 3–4), «Скопировать текст для OLX / Instagram».
7. Канал: продавец добавляет бота админом с правом публикации → бот получает `my_chat_member` и привязывает канал (`/internal/channels`, только для бота). Удаление бота из канала — отвязка.
8. Магазин: название, место на рынке, фото точки; профиль магазина снимает лимит. Значок «Проверенный магазин» — `POST /admin/shops/:id/verify` (админ).

**Модуль A — каталог и помощник** (`apps/api/src/modules/catalog/`):
- `GET /catalog` — фильтры (категория, цена, состояние, район, «только проверенные магазины»), сортировка (релевантность, новые, цена ↑↓), по 20 на страницу. Показываются только активные и не истёкшие объявления.
- Поиск по двум языкам:
  - сгенерированная колонка `search_vector`: русская морфология для RU и словарь `simple` для узбекского и названий моделей;
  - для узбекского слова ищутся по началу (`noutbuk` находит `noutbuki`), потому что узбекского стеммера в PostgreSQL нет;
  - триграммы ловят опечатки;
  - словарь местных написаний: «айфон / aifon», «макбук / makbuk», «пс5», «эирподс» и т. п. (`packages/shared/src/search.ts`).
- Метка цены «ниже / в рынке / выше на X%» берётся из справочника. Если модели там нет — из медианы похожих объявлений каталога за 90 дней (нужно минимум 3; диапазон — 20–80-й перцентиль). Эта же медиана теперь используется в проверке модуля B.
- Доверие к продавцу считается кодом, а не AI: проверенный магазин или ≥3 продажи через платформу → высокое; 1 продажа или аккаунт старше 30 дней → среднее; иначе «новый продавец».
- Избранное (`/favorites`) — со счётчиком в статистике продавца. Подписки на поиск (`/searches`): при публикации подходящего объявления бот присылает уведомление. Не чаще 3 в день на пользователя, без повторов, без уведомлений о своих объявлениях.
- «Написать продавцу» (`POST /listings/:id/contact`):
  - бот пересылает сообщение с маской «Покупатель из Ishonch интересуется…» и кнопкой «Ответить»; следующий текст отвечающего уходит собеседнику;
  - имена, юзернеймы и телефоны не раскрываются;
  - переписка хранится в `conversations` / `conversation_messages`;
  - не больше 20 новых диалогов в день на покупателя;
  - Mini App перед первым сообщением запрашивает у пользователя разрешение, чтобы бот мог ему писать.
- AI-помощник (`POST /assistant`):
  1. `assistant_query` на экономичной модели разбирает запрос. Задаёт не больше 2 уточняющих вопросов за диалог — после двух сервер сам переходит к поиску. На посторонние темы вежливо отказывает.
  2. Поиск идёт в базе по извлечённым фильтрам. Если ключевые слова слишком узкие — повторный поиск по категории и бюджету.
  3. `assistant_recommend` на сильной модели (Opus) выбирает 3–5 вариантов из реальных кандидатов и пишет плюсы, минусы и почему вариант подходит. Id, которых нет среди кандидатов, отбрасываются кодом.
  4. Если ничего не нашлось — кнопка «Сообщить, когда появится» сохраняет подписку с теми же фильтрами.
  5. `POST /assistant/compare` сравнивает 2–3 объявления. Таблицу строит код из данных, AI добавляет только вывод «лучше всего для…».
  6. Лимит — `ASSISTANT_PER_DAY` (10) запросов в день на пользователя.
- «Найти похожие у проверенных продавцов» из проверки (бот и Mini App) открывает каталог с этим запросом, фильтр — только проверенные магазины.

**Этап 4 — доставка и доверие** (`apps/api/src/modules/orders/`, `moderation/`, `trust/`):

- **Тарифы** `courier_tariffs`: цена по районам (откуда/куда, `null` = любой) и процент за перевозку наличных. Побеждает самая точная строка: пара районов → только «куда» → только «откуда» → по умолчанию. Сид: Ташкент 30 000, Бектемир/Сергели/Янгихаёт 40 000, 1% за наличные. Редактируются целиком через `PUT /admin/tariffs`.
- **Расчёт** (`quoteDelivery`, `packages/shared/src/delivery.ts`): доставка + сбор за наличные (кроме `delivery_only`), делится по `fee_payer` объявления (покупатель / продавец / пополам). Покупатель видит, сколько отдаст курьеру; продавец — сколько получит. Сумма фиксируется в заказе на момент оформления.
- **Заказ** («Купить с доставкой» → способ, район, адрес → `POST /orders`):
  1. Нужен телефон (тот же `requestPhoneAccess`, что у продавца). Не больше 5 открытых заказов на покупателя, один открытый заказ на объявление.
  2. Продавцу приходит сообщение с кнопками «Подтвердить / Отказаться» — без адреса и телефона покупателя. Счётчик «заявки» в статистике растёт.
  3. Подтверждение бронирует объявление (`reserved`: пропадает из каталога, нельзя заказать или написать). Остальные заявки на этот товар закрываются с уведомлением.
  4. Операторам уходит карточка: товар, сколько собрать наличными, адрес и телефоны обеих сторон, кнопки следующего статуса. Карточка идёт в группу `OPERATOR_CHAT_ID`, иначе в личку операторам и админам. Бот после нажатия перерисовывает карточку.
  5. Статусы: `new → confirmed → courier_assigned → picked_up → delivered | returned`; `cancelled` — покупатель/продавец до передачи курьеру, оператор до забора. Кто какой переход может сделать, описано в `ORDER_TRANSITIONS`. Смена статуса атомарная (compare-and-set), каждое изменение пишется в `order_events`, обе стороны получают уведомление.
  6. `delivered` → объявление продано через Ishonch (растёт доверие продавца), покупателя просят оставить отзыв. `returned` (отказ после осмотра) или отмена после брони → объявление снова в продаже (или в архиве, если срок истёк).
  - Частичные уникальные индексы в БД гарантируют один открытый заказ покупателя на объявление и одну бронь на объявление даже при гонках.
- **CourierProvider** (`orders/courier.ts`): `createShipment` при подтверждении, `cancelShipment` при отмене. Сейчас есть только `ManualProvider` — курьера бронирует оператор. Интеграция со службой доставки реализует тот же интерфейс и двигает статусы через `operatorSetStatus`.
- **Отзывы**: только покупатель, только после `delivered`, один на заказ, 1–5 звёзд и текст (телефоны и ссылки вычищаются). Средняя оценка видна в карточке продавца, `GET /sellers/:id/reviews` отдаёт последние отзывы. Если отзывов ≥3 и средняя <3, доверие к продавцу — «низкое», даже у проверенного магазина.
- **Жалобы** (`POST /listings/:id/complaints`): причина из списка и комментарий, одна жалоба от пользователя на объявление, не больше 10 в день. Когда открытые жалобы есть от 3 разных пользователей (`complaints_to_hide` в `settings`), объявление скрывается (`pending`). Продавец получает уведомление, модераторы — карточку с причинами и кнопками. Решение модератора закрывает жалобы.
- **Модерация при публикации** (`moderation/service.ts`):
  1. Телефон, карта, ссылка или @username в тексте → публикация отклоняется сразу, с подсказкой.
  2. Дубли по perceptual hash (dHash, расстояние Хэмминга ≤ 6, считается в SQL через `bit_count`). Свои же фото в живом объявлении → «поднимите существующее» (магазинам можно: одинаковый товар на складе). Фото из чужого объявления → на проверку.
  3. Почти тот же текст (pg_trgm ≥ 0,85, описание от 80 символов) у другого продавца в той же категории → на проверку.
  4. `listing_moderate` (экономичная модель, фото 512px + текст + рыночный диапазон) → `approved` / `needs_review` / `rejected` с причинами и советом продавцу на RU и UZ. Берётся более строгое из решения правил и AI.
  5. `needs_review` → `pending`, модераторам уходит карточка с кнопками; выбранные при публикации каналы сохраняются и получают пост после одобрения. `rejected` → продавец видит причину в «Моих объявлениях», может исправить и опубликовать снова.
  - Если AI недоступен (лимит бюджета, сбой, невалидный ответ), решают правила — публикация не блокируется.
  - Изменение текста активного объявления проходит модерацию заново.
  - `AI_MODERATION=false` оставляет только правила.
- **Срок публикации**: раз в час (`server.ts`) API напоминает продавцу за 3 дня до конца срока, с кнопкой «Продлить на 30 дней». Истёкшие объявления уходят в архив с той же кнопкой. Напоминание «захватывается» в БД, поэтому дублей нет и при нескольких инстансах.
- **Бан** (`POST /admin/users/:id/ban`): API перестаёт пускать пользователя, его объявления уходят в архив, открытые заказы отменяются с уведомлением второй стороны. Заказ, который уже у курьера, остаётся оператору. Админа забанить нельзя. Разбан не возвращает объявления автоматически: продавец публикует их заново, через модерацию.
- **Роли**: `ADMIN_TELEGRAM_IDS` → admin, `OPERATOR_TELEGRAM_IDS` → operator. Кнопки в группах бот передаёт в API от имени нажавшего, права проверяет API. Обычные сообщения в группах бот игнорирует.

**Этап 5 — админка и метрики**:

- **Где.** Раздел «Админка» внутри Mini App: вход через Telegram (initData), права по роли. Плитка на главной видна только персоналу; бот открывает её командой `/admin`, утренняя сводка — кнопкой. Код админки грузится отдельным чанком (~25 КБ), покупатели его не скачивают. Интерфейс персонала только на русском, как и карточки в чатах операторов и модераторов.
- **Админ** видит вкладки «Сводка», «Модерация», «Жалобы», «Заказы», «Пользователи», «Справочники», «Настройки». **Оператор** — только «Заказы».
- **Сводка** (`GET /admin/metrics?days=7|30|90`, дни по Ташкенту):
  - ключевые числа: пользователи (новые, активные), живые объявления, доставлено и оборот, доля возвратов после осмотра, расходы на AI относительно месячного лимита, что ждёт внимания (модерация, открытые жалобы, заказы без движения больше 24 часов);
  - воронка покупателя: приняли условия → искали в каталоге → открыли объявление → написали продавцу → оформили доставку → получили → оставили отзыв;
  - воронка продавца: начали объявление → опубликовали → подтвердили заказ → продали через Ishonch;
  - шаг воронки — число уникальных пользователей, сделавших его за период (а не строгая последовательность), процент — от предыдущего шага. Для малых чисел так честнее и не нужно склеивать сессии;
  - заказы по способам доставки, причины отмен, среднее время до доставки, сборы за доставку; модерация (опубликовано сразу / на проверку / отклонено), жалобы;
  - AI по функциям, таблица по дням (дни без активности скрыты);
  - `GET /admin/reports/orders.csv` — заказы для сверки с курьерами: `;`-разделитель и BOM, чтобы Excel открыл кириллицу.
- **Новые события** для воронки: `catalog_search` (первая страница, с числом результатов — запросы без результатов пополняют словарь написаний в `search.ts`) и `listing_viewed` (без своих объявлений и без персонала).
- **Модерация** — очередь `pending` с причинами AI, правил и жалоб, ссылками на похожие объявления, кнопками «Одобрить / Отклонить» (те же правила, что у кнопок в боте). Персонал открывает объявление в любом статусе.
- **Заказы** — открытые заказы с контактами, суммой к сбору, именем курьера и кнопками следующего статуса. Заказы без движения больше суток подсвечены.
- **Пользователи** — поиск по Telegram ID, бан с причиной и разбан, список заблокированных.
- **Справочники** — импорт цен из CSV, фильтр и удаление строк; редактор тарифов доставки.
- **Настройки** (`GET/PUT /admin/settings`) — проверок в день, запросов к помощнику в день (вопросы и сравнения), AI-черновиков и генераций текста в день на продавца, курс USD, лимит на AI, сколько жалоб скрывают объявление. Дневные квоты резервируются до вызова AI, поэтому параллельные запросы их не обходят. Значения проверяются; применяются в течение минуты без перезапуска.
- **Утренняя сводка.** Каждый день в `DIGEST_HOUR` по Ташкенту (по умолчанию 9) админам приходит отчёт за вчера: новые пользователи, проверки, объявления, заказы и доставки, возвраты, расходы на AI, а также список того, что требует внимания. День «захватывается» в `settings`, поэтому при нескольких инстансах API сводка не дублируется. `POST /admin/digest` отправляет её сразу.
- **Индекс для дублей.** dHash разбит на 8 байтовых полос (генерируемая колонка `phash_bands` + GIN-индекс). Если хэши отличаются не больше чем в 6 битах, хотя бы 2 полосы совпадают точно. Поэтому индекс находит кандидатов, а `bit_count` их проверяет — без перебора всех фото.

Фото отдаются по подписанным URL (`/photos/:id?s=…`), поэтому работают в `<img>` без заголовков авторизации, а черновики нельзя перебрать по номеру.

## Аудит (после этапа 5)

Полная перепроверка (безопасность, состояния, производительность, клиент и деплой) нашла и исправила:

- **Доступ:**
  - сравнение и избранное больше не показывают чужие черновики;
  - решения модератора и скрытие по жалобам нельзя обойти через архив;
  - лимит снимается только с проверенного магазина;
  - роли персонала следуют `ADMIN/OPERATOR_TELEGRAM_IDS`;
  - CSV защищён от формул;
  - аккаунт с открытыми заказами не удаляется;
  - nginx не пропускает служебный токен снаружи;
  - production не стартует с токеном-заглушкой.
- **Состояния:**
  - смена статуса в публикации, одобрении и скрытии атомарна (двойное нажатие или два модератора больше не публикуют дважды);
  - заявки на снятый с продажи товар закрываются, без ответа продавца — через 48 часов;
  - живое объявление нельзя перегенерировать целиком;
  - у забронированного нельзя менять текст и цену;
  - распознавание телефонов не путает цены, IMEI и серийные номера.
- **Производительность:**
  - карточки собираются пакетно (фиксированное число запросов на страницу);
  - дневной ряд метрик — сгруппированными запросами;
  - подписки предфильтруются в SQL;
  - дубли фото ищутся по индексу;
  - нечёткий поиск требует номера модели;
  - добавлены индексы и лимит 40 МП на фото.
- **Клиент и бот:**
  - защита от гонок ответов и двойных нажатий;
  - ожидание телефона с таймаутом;
  - экран ошибки вместо белого экрана после деплоя;
  - проверки в боте идут в фоне и не блокируют других пользователей;
  - устаревшие кнопки не крутятся вечно.
- **Деплой:**
  - nginx перерезолвит `api`, не кэширует `index.html`, ставит заголовки безопасности и таймаут 150 с;
  - API и бот корректно получают SIGTERM;
  - healthcheck у API;
  - логи идут и в `docker logs`;
  - сид не возвращает удалённые админом цены.

Рекомендации аудита реализованы:

1. **Масштаб:**
   - очередь фоновых задач в PostgreSQL (`jobs`, `FOR UPDATE SKIP LOCKED`, повторы с паузой) для постов в каналы и рассылки по подпискам; повтор не дублирует пост в канале;
   - нечёткий поиск и цены по модели — через операторы `<%` и `%` по триграммным индексам (пороги задаются параметрами соединения);
   - бюджет AI — счётчик `ai_budget` по месяцам и классам моделей, отдельный лимит для сильной модели (`ai_strong_monthly_limit_usd`);
   - бот — webhook или `@grammyjs/runner` (параллельно, но по порядку внутри чата); состояние «Ответить» — в БД.
2. **Безопасность:**
   - лимиты частоты по пользователю Telegram (`@fastify/rate-limit`: AI, сообщения, заказы, жалобы, загрузки);
   - не больше 30 сообщений в час от участника в диалоге и 3 заявок на товар в сутки;
   - журнал действий персонала (`admin_audit`, вкладка «Журнал» в админке, `GET /admin/audit`);
   - схема `X-Telegram-User`;
   - запуск Mini App действует 4 часа, после этого — экран «откройте заново».
3. **UX:**
   - стек экранов («Назад» возвращает к поиску, после оформления — к объявлению);
   - попапы Telegram вместо `window.confirm`;
   - CSV через `downloadFile` по подписанной ссылке на 5 минут;
   - вход `@ishonch/shared/client` без zod и ленивая загрузка второго языка: основной бандл 490 → 341 КБ (gzip 147 → 103 КБ).
4. **Деплой:**
   - образы MinIO через `MINIO_IMAGE` и `MINIO_MC_IMAGE` — проверенный тег закрепляется в `.env`;
   - ротация логов `deploy/logrotate-ishonch`;
   - миграции под advisory lock;
   - ежечасные задачи и сводка — на одной реплике;
   - проверка словарей в CI.

Ограничения, о которых стоит помнить:

- Лимиты частоты хранятся в памяти каждой реплики API. При нескольких репликах фактический лимит умножается на их число; для строгого общего лимита нужен Redis.
- Склейка альбомов фото в боте работает в памяти: запускайте одну копию бота. Runner и так обрабатывает обновления параллельно.
